# 标签审计方法

本文件是 `SKILL.md` 第 8 节「批量改动的纪律」的展开：怎么把一棵标签树查干净，以及改之前要准备什么。

这里的筛查维度都是通用的 —— 具体用哪套一级分类完全取决于实例使用者。审计时先用 `list_tags` 看清楚现有树有几层、哪些分支深、哪些分支只有一层，再决定哪些是不正常。

## 全量审计执行流程

目标：把**所有未完成、未归档**的 memo 与五条原则逐条对照，产出一份可执行的调整建议。全程只读。

### 1. 圈定范围

审计范围是 `state == NORMAL`。两个容易错的地方：

- `list_memos(state: "NORMAL")` **会把 COMPLETED 一起返回**（服务端把"常规视图"定义为 NORMAL + COMPLETED）。所以拉完后必须对每条再判一次 `state == "NORMAL"`，否则已完成的条目会混进结果。
- `search_memos` 只看 NORMAL 且不可分页，不够用于全量；审计要用 `list_memos` 分页。

分页直到 `has_more == false`，不要只取第一页（单页上限 100）。

### 2. 拉快照

需要两份数据：

```
list_memos(state: "NORMAL", page_size: 100, page: 0, 1, 2, …)   → memos
list_tags()                                                      → tags
```

落盘成：

```json
{
  "memos": [
    {"name": "memos/abc", "content": "#一级/二级 正文…", "state": "NORMAL",
     "tags": ["一级/二级"], "plan_start_time": 1767225600}
  ],
  "tags": [{"tag": "一级/二级", "count": 12}]
}
```

`content` 必须带全文（脚本不看正文内容，但保留它方便你回看某条为什么被判低置信度）。`tags` 用 MCP 返回的数组即可，不要自己从正文正则提取 —— 服务端的解析器才是唯一标准。

### 3. 跑脚本

```bash
python3 scripts/audit_tags.py snapshot.json --json suggestions.json --limit 20
```

脚本是纯本地的：不联网、不调用 MCP、不写回任何 memo。它做的只有分类和排序。

### 4. 解读报告

报告结构固定：概览 → 同义标签组 → 问题分布表 → 按问题分组的明细 → 下一步。每条建议都带 `confidence` 和 `needs_user`。

按这个顺序处理：

| 优先级 | 问题类型 | 为什么 |
|---|---|---|
| 1 | `SYNONYM` | 客观等价，改法唯一，最不容易谈错 |
| 2 | `NO_TAG` | 必须先问用户挂哪个分支，不能自己编 |
| 3 | `MULTI_TAG` | 要判断是否真横跨两个分支 |
| 4 | `DEPTH_TOO_SHALLOW` / `MID_LAYER` | 要看正文才能决定下沉到哪层 |
| 5 | `LOW_REUSE` | 只是提示，可能用户就是为单条内容开的专用分支 |

`MID_LAYER` 的判据是「子分支合计用量 ≥ 父级用量」—— 只有主体已经细分下去、父级却还压着存量时才提示。父级本身就是主用节点时不会报，避免把每个分组容器都当成问题。

### 5. 交付建议

把报告转成给人看的清单，每条包含：memo 标识 + 当前标签 + 建议动作 + 需要确认什么。不要直接把脚本的原文贴给用户（里面全是英文码），也不要未经确认就批量改。

用户确认后，回到 `SKILL.md` 第 8 节的纪律执行：备份 → 单条验证 → 分批 → 复核。

## 建立索引

审计的第一步不是看标签列表，而是建立「标签 → memo」的对照关系。`list_tags` 只给计数，看不到具体是哪几条挂在这个标签下。

1. `list_tags()` 拉全量标签和计数，先看整体形状：一级分支有几个、哪些子分支只有一两条、哪些深度和其他分支明显不同
2. `list_memos(page_size: 100)` 分页拉全量（注意 `has_more` 和 `page`），把 `name` / `content` / `tags` / `state` 落到本地
3. 在本地把每条 memo 的标签拆开，按标签聚合，得到「每个标签 → 哪些 memo」

有了这份索引，后面所有筛查都只是本地集合运算，不必反复打接口。

归档条目不在 `list_memos` 的默认结果里，需要单独拉 `state: ARCHIVED`。审计时建议把归档也算上 —— 它们同样占着标签名，同义标签往往在归档区残留。

## 六个筛查维度

### 1. 单层标签

没有任何 `/` 的标签，比如 `#todo`、`#临时`、`#待定`。

单层本身不是错 —— 如果整棵树就只有一层，那它就是这套体系的正常形态。问题出现在**多层树里夹着单层标签**：主体分支都是 `#一级/二级`，个别标签却只有一级，它们没有父级归属，既不能随父级归组也不会出现在父级的筛选结果里。

判断方法：先看 `list_tags` 里各标签的层级分布，跟主体形态对比，而不是预先假定几层才对。

处理：在现有树里找最贴近的分支归进去。如果确实无类可归，**先问使用者**，不要自己新开一级。

### 2. 挂在中间层

有更深的分支存在，但 memo 却挂在父级上。比如树里已经有 `#a/b/c1`、`#a/b/c2`，却还有一批 memo 直接挂 `#a/b`。

不一定都是错的 —— 父级有时承担"这一类里暂时没细分的杂项"的角色。判断方法是看这批 memo 的正文：如果它们各自明显属于某个子分支，就该下沉；如果是真的杂项，保留在父级反而合理。

处理：逐条看正文再决定，不要批量下沉。

### 3. 同义标签对

同一个概念有多种写法，是最常见、也最值得清理的一类。常见形态：

- 分隔符不同：`#a/billing` 与 `#a__billing`（`__` 这种老式分隔符会让层级失效）
- 大小写不同：`#a/Billing` 与 `#a/billing` —— 解析是大小写敏感的，这确实是两个标签
- 中英混写：`#a/memodo` 与 `#a/Memos`
- 层级深度不同：`#a/审计` 与 `#a/审计/token`（前者可能是后者没细分时的粗略版）

处理：选定一个保留写法，把另一个改写过去。这是批量改动里量最大的一类，务必先备份、先单条验证。

### 4. 一条 memo 挂多个标签

默认应该是每条一个。挂多个的条目要逐条确认：是真的横跨两个独立分支，还是当初随手加了个维度，导致这条内容在两个分支里重复出现、统计被重复计数。

处理：能归到主分支一个的就收敛成一个；确实需要两个的保留，但记下来问使用者是否属于例外。

### 5. 无标签的 memo

一条标签都没有的条目，在列表、统计、日历里都是黑户，只能靠全文搜索捞到。

处理：逐条看正文生成候选，**带着候选问使用者**要挂哪个分支 —— 这类条目的归类往往比改标签更需要人工判断。

### 6. 归类存疑

标签本身合法，但和正文内容对不上。

处理：以正文为准，但不擅自改。这类必须先跟使用者确认 —— 你无法判断是标签打错了，还是正文写错了（或者两者都对，只是命名有歧义）。

## 改动流程

```
备份 → 单条验证 → 分批执行 → 复核
```

**备份**：把全量 `name` + `content` 写到本地文件。这是唯一的回滚手段，`update_memo` 没有历史版本。

**单条验证**：挑一条同时含「要改的标签」和「不能动的正文」的 memo，改完读回，确认：

- 旧标签彻底消失（正文里每一处都改了）
- 新标签能被解析到（`get_memo` 返回的 `tags` 里有它）
- 正文其余部分逐字未变

**分批执行**：一次改 10–20 条，每批结束抽查。不要一口气发几百个请求 —— 中途出错时你无法定位是哪一条写坏的。

**复核**：重新 `list_tags`，确认：

- 旧标签的计数归零并消失
- 新标签的计数等于「原新标签计数 + 迁移过来的条数」
- 没有产生新的同义标签（迁移时手滑写成另一种分隔符很常见）

## 复核清单

批量改完逐项确认：

- [ ] `list_tags` 里旧标签已消失
- [ ] 新标签计数与迁移条数对得上
- [ ] 抽查 3–5 条 `get_memo`，正文完整、`tags` 投影正确
- [ ] 原本多标签的 memo 仍保留该保留的标签（替换语义容易误删）
- [ ] 归档区（`state: ARCHIVED`）也已处理，没有残留旧标签
- [ ] 备份文件保留，直到使用者确认结果无误

最后一条常被忽略：`update_memo` 的 `content` 是整体替换，如果修改时手上只有部分正文（比如从搜索结果里截取的一段），写回去就会截断原文。所以任何批量脚本都必须基于 `get_memo` 拿到的完整正文来改。

## 遇到需要新建分支时

审计经常会发现"这批内容没有合适的归属"。这时不要顺手新建一个分支把它塞进去，先停下来确认：

- 现有树里真的没有语义接近的分支吗？（再看一遍 `list_tags`，尤其是低频分支）
- 如果要新建，它挂在哪一级下？命名沿用现有风格（语言、分隔符、单复数）吗？
- 新建后，将来同类内容都能落到这里吗？还是只为这一条服务？

把这三个问题连同建议一并向使用者提出，得到确认再建。新建分支是不可逆的膨胀 —— 一旦有人开始用，就很难再合并回去。
